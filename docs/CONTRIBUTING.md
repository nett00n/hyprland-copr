# Contributing

`packages.yaml` is the single source of truth for every package; `packages/<name>/<name>.spec`
files are generated from it (via `templates/spec.j2`) and committed, editable. Everything else
— maintainer runbook, `packages.yaml` schema reference, `scripts/lib/` internals (every module
has a docstring) — run `make help` or see `docs/operations.md` / `docs/packaging.md`.

## Setup (one-time)

```shell
cp .env.example .env        # packager identity + defaults; fill in your name/email
make setup-venv              # creates .venv, installs requirements.txt
make container-build         # builds the Fedora 43 container image (FEDORA_VERSION=X for others)
```

## Adding a new package

One command:

```shell
make add-new URL=https://github.com/org/repo
```

Registers the git submodule and scaffolds the `packages.yaml` entry in one step. Step by step,
that's:

```shell
git submodule add <url> submodules/<org>/<name>
make add-submodule PACKAGE=<name>       # registers ignore=dirty in .gitmodules
make scaffold-package PACKAGE=<name>    # adds the packages.yaml entry
```

`make list-tags PACKAGE=<name>` (or with no `PACKAGE` for all submodules) shows available
upstream tags first, if useful.

Scaffolding produces an entry like:

```yaml
packages:
  <name>:
    version: "1.2.3"
    release: 1
    license: GPLv3
    summary: One-line description
    description: |
      Longer description.
    url: https://github.com/org/<name>
    source_name: <name>  # set if tarball top-level dir differs from package name
    sources:              # auto-indexed: Source0, Source1, ...
      - url: "%{url}/archive/refs/tags/v%{version}.tar.gz#/%{name}-%{version}.tar.gz"
    build_system: cmake   # cmake | meson | autotools | make
    depends_on:           # local packages that must build first (authoritative)
      - hyprutils
    build_requires:
      - cmake
      - pkgconfig(wayland-client)
    files:
      - "%license LICENSE"
      - "%{_bindir}/<name>"
```

`depends_on` overrides the `-devel` heuristic used when absent — it's the authoritative
dependency-ordering source. `scaffold-package.py` auto-detects it from `build_requires` entries
matching existing package keys (`-devel` and `pkgconfig()` forms). `make stage-validate` warns
about `build_requires` entries that reference local packages but are missing from `depends_on`.

Then:

1. Fill in the `FIXME` fields the scaffold left behind.
2. Add the package to the relevant `groups` entry in `packages.yaml` (see `docs/packaging.md`)
   so it shows up in the grouped build report.
3. Build it: `make full-cycle PACKAGE=<name> FEDORA_VERSION=43 COPR_REPO=nett00n/hyprland`
   (`COPR_REPO` unset skips the Copr push).
4. On failure, `make stage-log-analyze PACKAGE=<name>` — see `docs/operations.md` for reading
   build logs and the cache/force-rerun model.
5. Fix issues in `packages.yaml` (add `build_requires`, exclude incompatible plugins, etc.) and
   retry.
6. `rpmlint packages/<name>/<name>.spec`
7. Commit, open a PR.

## Code quality and linting

Everything runs inside a container (podman/docker, auto-detected) plus the host `.venv`:

```shell
make lint          # lint-ruff + lint-flake + lint-mypy + lint-rpm + lint-yaml
make fmt            # fmt-ruff + fmt-yaml + normalize-paths + sort-lists
make pre-commit     # validate-packages + test + lint + fmt (COVERAGE=1 for a coverage report)
```

Run `make pre-commit` before and after any change. It's also what gates `make update-daily` and
what CI runs on every push/PR (lint + test, natively via `NO_CONTAINER=1` — CI can't nest
privileged containers).

## Checklist before opening a PR

- [ ] `packages.yaml` entry is complete and correct
- [ ] `make stage-validate PACKAGE=<name>` passes with no errors
- [ ] `rpmlint` passes with no errors
- [ ] Builds cleanly with `make stage-mock PACKAGE=<name>`
- [ ] `Source0:` points to an upstream release tarball (not a manual archive), with
      `#/%{name}-%{version}.tar.gz` to avoid filename collisions between packages at the same
      version
- [ ] No bundled C/C++ libraries (Go/Rust vendor tarballs are acceptable — see
      `docs/packaging.md`)
- [ ] RPM `%changelog` entry looks correct (auto-generated by the spec stage from GitHub release
      info + packager identity — not `CHANGELOG.md`)
- [ ] `docs/CHANGELOG.md` entry added if this PR changes automation behavior (see below)

## Changelog

`docs/CHANGELOG.md` tracks changes to the automation itself — Makefile targets, script
behavior, `packages.yaml` schema, build pipeline stages, breaking contributor-facing changes.
It does **not** track routine package adds/version bumps/release increments (that's
`update-daily`'s job — see `packages.yaml` git history or `docs/full-report.md` instead).

Format: newest section first, dated `## YYYY-MM-DD` headings, one bullet per entry as
`- <Added|Changed|Fixed|Removed>: <what changed>`. Add an entry whenever your PR changes
automation behavior; skip it for docs-only fixes, package additions, and version bumps.
